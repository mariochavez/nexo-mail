How nexo_mail is built

Read-only AI email triage for Apple Mail, Gmail & HEY. It turns three inboxes into one briefing — digest.json plus a self-contained dashboard.html — using agents and skills, with the Ruby library kept to just tools and orchestration.

Two core ideas

Everything else follows from these.

idea 01

Agent = model + harness

A model does the reasoning; the harness (nexo_ai on ruby_llm) supplies the tools, the skills, the read-only permission gate, the fenced sandbox, and the model→tool→model loop.

idea 02

Ruby = tools + orchestration only

The library provides read-only mail tools and a thin workflow. Extraction, the digest, the dashboard, and snapshots all happen on the agent + skill side — behavior is tuned by editing Markdown, not Ruby.

The pipeline

Four stages. Stage 1 fans out to three source agents; the workflow runs the rest in order. Click a stage for detail.

Inboxes — Apple Mail · Gmail · HEY
▼read read-only, through tools
Each source agent reads its inbox through read-only tools and writes a JSON array of classified items — bucket, category, and the entities that matter. Gmail and HEY share one data-driven EmailSource (built from a Sources descriptor); Apple Mail keeps its own AppleMailSource for its MCP server.
  • Skills: email_triage, financial_summary, interest_radar.
  • HEY pulls all three boxes: Imbox → action/fyi, Feed → topics, Paper Trail → payments.
  • Fanned out concurrently via Nexo.concurrent; a failing source degrades to “no file” and the run continues.
▼apple-mail.json · gmail.json · hey.json
The Synthesize agent reads the per-source files and produces digest.json (canonical data) + inbox-digest.md (terminal).
  • De-dup twice: cross-source (same email in two inboxes) and cross-group (each message shows in only its strongest surface).
  • Money rolled up per currency; schedule ordered; stories, per-person notes, and topic briefings (2–3 bullets) written.
  • Skills: inbox_synthesis, financial_summary, interest_radar.
▼digest.json + inbox-digest.md
The Publisher runs the dashboard_designer skill’s bundled render script over its template and digest.json, via the Shell tool.
  • The design lives in a fixed, versioned template — the model does not author HTML, so every run is byte-identical.
  • Paths come from [dashboard] config (template / renderer / ruby).
  • The script escapes the untrusted email text so it can’t break out of the data blob — safety in code, never trusting the model.
▼dashboard.html
The Archivist copies the run’s artifacts into a timestamped snapshot and prunes old ones to the configured retention.
  • Uses the ArchiveRun and PruneSnapshots tools; the agent decides, the bounded tool does the file work.
  • nexo-triage --prune-snapshots [N] runs the Archivist prune-only.
▼archived & pruned
snapshots/<ts>/ — digest.json · dashboard.html · inbox-digest.md

Safety model

Read-only by construction, with exactly one scoped exception.

Read-only mail, three ways

MCP fail-closed gate · IMAP EXAMINE · hardcoded read subcommands, no general shell.

Fenced writes

Every agent’s :local sandbox is rooted at the workspace; the path guard rejects ../ and symlink escapes. Beyond read-only, agents get only :write.

One shell exception

The Publisher alone gets :shell, only to run the render. It attaches no mail tools. Mail agents’ authorize!(:shell) raises.

Publisher: shellall others: none

Bounded destructive tools

PruneSnapshots deletes only inside the snapshots dir. The agent decides to prune; the tool does it deterministically.

Opening the read-only guarantee — deliberately and narrowly

The dashboard is a skill-owned template rendered by a script, and running a script needs a shell. Nexo attaches its Shell tool only when the sandbox supports :shell (Local does) and permissions allow it — a read-only agent has neither. So one capability was added to exactly one agent. Here is precisely what changed and why it stays safe.

What was opened — one line, one agent. The Publisher's permission allow-list gained :shell; mode stays :read_only. Nothing else changed.

SourceAgent (all mail agents)   Permissions(mode: :read_only, allow: %i[read glob write])
Publisher only                  Permissions(mode: :read_only, allow: %i[read glob write shell])

Why it stays safe

• The Publisher attaches no mail tools — it can't reach any inbox; it only reads the already-produced digest.json.
• The script it runs is developer-authored and bundled with the skill (from config-driven paths), never model-generated.
• The shell runs inside the :local sandbox with a narrowed ENV (PATH/HOME/LANG only).
• The XSS escaping is done in the script (code), not trusted to the model.
• The workflow hands the exact command; the Publisher just runs it.

Alternatives considered

Ruby render tool / ERB in the library — rejected: keeps artifact generation in the app, against “Ruby = tools + orchestration only.”
Orchestration runs the script (no shell) — safest, but the decision was for the agent to execute it through the skill.
Embed the scaffold in skill text (model re-emits ~300 lines) — no shell, but not byte-identical and unreliable on small models.

The blast radius, stated plainly. An LLM now holds a sandboxed shell. It is scoped to the Publisher — an agent with no mail access, reading only derived data, running a fixed developer-authored script. Every inbox-touching agent remains strictly read-only. Verify it yourself: AppleMailSource.permissions.authorize!(:shell) raises; Publisher.permissions.authorize!(:shell) does not.
